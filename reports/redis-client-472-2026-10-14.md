# Client 472 Redis interruption — 2026-10-14

All incident times below are IST. Investigation was read-only; no production restart, configuration change, or deployment was performed.

## Confirmed incident

The affected process was `quicktricks-socket` (PM2 28) on `webserver2-2`, serving `socket.quicktricksbysahilsir.com`. The separate GCP encoder `quicktricks-livestream` remained running through the incident. The active encoder class from 13:07:59 to the user End at 14:00:33 was `6ace40f7abbe7476bf69c7a2`, client 472.

The socket process's first recorded probe failure was **13:27:53**: `pubClient PING timed out after 5000ms`. Three failures led to a forced reconnect at **13:28:13**. Ordinary callers immediately logged `PubClient not ready, attempting reconnection`; at **13:28:14**, the watchdog's own reconnect failed with `Socket already opened`.

Subsequent failed probes caused the watchdog's `onUnrecoverable` callback to call `process.exit(1)`. PM2 recorded seven restarts at **13:30:13, 13:32:49, 13:34:46, 13:35:55, 13:37:41, 13:41:17, and 13:47:53**. Redis recovery after a restart does not establish that the triggering stall was cured: failures recur across fresh processes.

Additional transport errors: connection timeout at **13:29:58**, and `read ECONNRESET` at **13:47:59**. Both subscriber and publisher probes failed in several later intervals. Last observed recovery was publisher reconnect at **13:48:30**. Later commands and endStream events succeeded.

## Confirmed recovery defect

Deployed `backend/PubSubManager.js` getters call `.connect()` whenever `isReady` is false. The watchdog in `backend/lib/redisWatchdog.js` disconnects the same client, waits one second, then calls `.connect()`. During that gap a getter can open the client first, so the watchdog's call throws `Socket already opened`. Its next three failed probes then terminate the entire socket process.

A local harness using the deployed watchdog module and a simulated stalled client reproduced this race and escalation in three consecutive runs. This verifies the recovery race, **not the cause of the original Redis stall**.

## Checks against alternative explanations

- GCP encoder retained PID 708 and kept receiving Redis events during the socket-server failure window; no corresponding encoder Redis transport error was recorded that day.
- Historical host CPU averaged about 93% idle and available memory about 37 GB from 13:20 to 13:50. Network interface utilization was below 0.2%. These ten-minute averages cannot exclude a short spike or one blocked Node event loop.
- A fresh connection from the socket host later returned PING in 3 ms. Redis INFO showed 49 clients, zero rejected connections, zero evicted keys, and approximately 394 days of uptime. These are post-incident measurements, not proof of incident-time health or absence of proxy/failover activity.
- The retained newest 25 SLOWLOG entries had no command in the incident window. This does not measure network delivery, client queues, or managed-service bandwidth limits.
- Redis output was approximately 4.77 MB/s at the later measurement; current client output buffers were zero. Neither proves incident-time congestion or throttling.
- The previously adjusted Media List index and RESP decoder reset patch are present in the deployed source. Media List fetches indexed IDs with a default limit of 100; the old full timeline scan is absent.

## Conclusion and next discriminating measurement

**Confirmed:** unanswered Redis probes triggered watchdog reconnects and seven full socket-process restarts; competing reconnect ownership is a reproducible defect that interferes with recovery.

**Unresolved:** what caused the first unanswered probe. The evidence does not justify blaming Redis server execution, network loss, managed-service throttling, or client queue/decoder state exclusively.

To identify that trigger on the next occurrence, capture independent-connection PING latency alongside app-client PING latency, event-loop delay, TCP retransmissions/connection state, and command queue/reply-volume measurements on this host. Compare Redis Cloud throughput/latency/connection events for **08:00–08:20 UTC (13:30–13:50 IST)**, extending the start to **07:55 UTC** to cover the initial stall. A healthy independent connection while the app stalls points toward app/client state; both stalling with TCP retransmissions points toward the network path; both stalling with provider latency or bandwidth-limit events points toward Redis/service congestion.

A targeted recovery fix should give one component ownership of connect/reconnect and prevent getters from opening clients during watchdog recovery. That change would address the demonstrated race; it should not be described as a fix for the unknown initial stall.

### Revised conclusion

The evidence now favors **a failure specific to the QuickTricks command connection or its service handling**, followed by the demonstrated reconnect-ownership race and watchdog process exits. A blanket Redis/server-host outage and the old large Media List read explanation are unsupported by this comparison. The retained evidence still cannot uniquely identify the initiating fault. Provider history for 13:27–13:49 and 14:53–14:55 IST, or simultaneous independent/app-client probes during a recurrence, is needed to distinguish selective service throttling, an individual TCP-flow failure, and an app-client protocol/queue stall.

## Fault-layer pinpoint from original error stacks

A further check inspected the exact error stacks, rather than treating every timeout as equivalent:

- **13:29:58:** `ConnectionTimeoutError` originates from `@redis/client/dist/lib/client/socket.js:177:124`, through Node's `Socket._onTimeout`. The installed client's `createSocket()` applies the configured 10-second socket timeout before connecting, then executes `.setTimeout(0)` inside the TCP `connect` handler. Therefore this error represents a TCP connection that did not reach the connect handler within the timeout. It is distinct from the watchdog's application-level `PING timed out after 5000ms` error. Incoming socket requests continued to be logged during this period, so a sustained total event-loop freeze is not supported.
- **13:47:59:** `read ECONNRESET` originates from Node's `TCP.onStreamRead`, with `syscall: read` and errno -104. It occurred about five seconds after a fresh socket-process boot, and the same error propagated into message-history reads. The watchdog had not yet issued a force-reconnect in that new process (that happened at 13:48:29).

These stacks establish **real TCP connection failures during the episode**, beyond the application's probe/recovery symptoms. A pure RESP decoder stall is insufficient to explain the TCP connection timeout and reset. Neither error identifies whether the underlying actor was packet loss/filtering, an endpoint proxy, or Redis-managed service behavior. It also remains possible that an app-client stall initiated the first 13:27:48 gap and later transport failures compounded it; the first-gap logs contain no corresponding transport error.

The strongest supported classification is now: **QuickTricks' connection to the old shared Redis experienced transport failures during the incident; its competing reconnect handlers and watchdog escalations amplified those failures into full client-socket restarts.** The exact initiating infrastructure condition remains unverified pending provider history or incident-time independent connection/TCP probes.
