# Slice: 1080p HLS rung, per client

**Goal:** a client can be switched to a 1080p top rung, for both uploaded videos and live classes, and the
rung spends the fewest bits that keep it visibly better than 720p. Every client not switched on keeps
today's 240/360/480/720p ladder with no change to its encode.

**Why it's a slice:** the rung is produced by two transcoders (video-transcoder for uploads, livestream for
live), and the viewer side (`ls`) had the quality menu hard-coded. No LMS change: `hlsAsset` points at the
master playlist, and quality strings are free-form there.

**Decisions (user, 2026-10-19):** uploads and live both; per-client switch is an env var; no separate 1080p
MP4 (downloads come from the HLS); new uploads only, no backlog re-transcode.

## The switch

| surface | variable | effect |
|---|---|---|
| uploads (video-transcoder listener) | `${envPrefix}_HLS_1080P_<clientId>=true` | Job profile gains `hls: { maxHeight: 1080 }` → manager adds `HLS_MAX_HEIGHT=1080` → container adds the 1080p rung when the source's displayed height ≥ 1080 |
| live (livestream encoder) | `LIVE_HLS_1080P_CLIENTS=<comma ids>` (target: Vidyagram `781`, on its own encoder VM) | ffmpeg probes the RTMP input; folder `4` = 1080p rung when the input is ≥ 1080 tall. Malformed list fails boot. Unlisted: no probe, argv pinned to `bfc1512` by test |

The prefix is the client's **intake queue**, not the client. Quicktricks (472, secured R2) uploads through the
secure lane, so its variable is `CF_SECURE_HLS_1080P_472`. Any value other than `true`/`false`/empty fails
the listener boot, naming the variable (a typo never silently stays 720p).

## Hops

1. **video-transcoder** (uploads). `src/intake-routing.js` `resolveQueueProfile` + `validateQueueProfiles`;
   `gpu-server/job-manager/manager.js` (profile → `HLS_MAX_HEIGHT`); `container/hls-ladder.js` (the ladder
   table, `rateArgs`, `displayedHeight`) used by `container/index.js` `processVideoToHls`. The 1080p rung is
   capped constant-quality (`-cq` on NVENC, `-b:v 0`, maxrate ceiling); the four base rungs keep their ABR
   args byte for byte. Only jobs with the profile run the extra ffprobe.
2. **ls** (viewer). `components/HLSVideoPlayer.tsx` builds the quality menu from `hls.levels`, so 1080p shows
   only on streams that carry it (and 240p, which the old static list hid, now shows too).
3. **livestream** (live). Built 2026-10-20 for **Vidyagram (781)**, not quicktricks (user, 2026-10-21). Branch
   `feat/vg-live-1080p` (cut from `launch/quicktricks-v2` 6fb66fb, commit `303c2b3`, local, not pushed; worktree
   `~/Projects/worktrees/livestream-1080p`). Never merge it into `launch/quicktricks-v2` (Vidyagram rule). `backend/lib/liveLadder.js`
   is the one rung table (folder, size, rate, profile/level/preset) read by `streamLifecycle.js` (command,
   reconnect helpers), `watchers.js`, `hls.js` (VOD finalize + fallback master), `segmentReconciler.js`,
   `fileUpload.js` (VOD playlist upload) and `ecs.js` (1C download ladder = base rungs, still capped at 720p).
   Folder `0` stays 720p and the timing reference; base rungs `0..3` unchanged. FFmpeg creates folder `4`
   itself (the watchers make only `0..3`), so `4/` on disk records that a stream carries the rung; a
   reconnection keeps the rung set it started with (no 1080p playlist covering only the tail). The probe
   (`lib/probeInputHeight.js`, ffprobe, 8 s cap, failure → base ladder) runs only for listed clients and holds
   the `STARTING` slot; a cleanup or reconnection during it cancels that start.
   **The live rung:** capped CRF 29, maxrate 2500k / bufsize 5000k, High 4.1, `-preset:v:4 veryfast`,
   `-x264-params:v:4 bframes=3:rc-lookahead=10:mbtree=1:sliced-threads=0` (zerolatency stays on the base rungs;
   verified on the box: rung 4 has B-frames, rung 0 I/P only, segment PTS aligned). ~0.4 s more encoder delay
   on that rung only.
   **CPU (livestream-testing-raghav, 2026-10-20):** Intel Xeon Platinum 8581C @ 2.3 GHz, 4 cores / 8 vCPU (HT),
   29 GB. Today's live input (quicktricks 472) is **1280x720 @ 24 fps** Constrained Baseline ~2.5 Mbps, and its
   4-rung encode runs ~1.05 vCPU. Real-time bench (`-re`, nice 19, 60 s of a 1080p30 class, next to a live class):
   base 4 rungs from a 1080p input 1.69 vCPU; + 1080p rung medium/zerolatency 3.01; veryfast/zerolatency 2.22;
   **veryfast + lookahead (shipped) 2.28**. All held real time. Peak concurrency in the pm2 logs (10-17..10-20):
   2 quicktricks classes → ~4.6 vCPU with both at 1080p.

## Downloads

1C (`gpu-server/hls-to-mp4-container/ffmpeg.js:7`) re-encodes downloads into a fixed 720/480/360/240 MP4
ladder from the HLS master, so a 1080p rung changes the source it reads from, not the download sizes. If the
apps download HLS directly instead, their download picker will offer 1080p.

## Bitrate evidence

`reference/encode-sweep-2026-10-13/sweep_1080.py` → `1080/results_1080.csv` (2026-10-20). Same smartboard class
and windows as the 10-13 sweep (W1 densest minute, W2 typical), reference = the native 1080p window, VMAF v0.6.1
(1080p-display model) after upscaling every encode to 1920x1080. x264 slow, closed 4 s GOP, High profile, standing
in for NVENC. One run per point; encodes rerun from cache.

| encode | W1 kbps / VMAF | W2 kbps / VMAF |
|---|---|---|
| today's 720p (ABR 1200k), on a 1080p screen | 1209 / 91.2 | 1212 / 92.0 |
| 1080p fixed target 2500k (the naive rung) | 2525 / 97.1 | 2525 / 97.4 |
| 1080p CRF 27 | 1921 / 96.1 | 1550 / 96.0 |
| **1080p CRF 29 (chosen)** | **1487 / 94.7** | **1199 / 94.7** |
| 1080p CRF 31 | 1142 / 92.9 | 919 / 93.1 |

Chosen: CQ 29, maxrate 2500k, bufsize 5000k. On a typical minute it costs the same bits as today's 720p rung for
+2.7 VMAF; against a fixed 2.5 Mbps rung it saves 41 to 53% of the bits for −2.4 to −2.8 VMAF. CRF 31 sits within
1.1 to 1.6 points of today's 720p, so the rung would barely earn its place. What limits the numbers: this
class's own entropy (static board). A webcam-heavy class will spend more, up to the 2.5 Mbps ceiling.
The GPU path is measured separately below (NVENC evidence); other classes are not measured.

## Live bitrate evidence

`reference/encode-sweep-2026-10-13/sweep_1080_live.py` → `1080/results_1080_live.csv` (2026-10-20). Same class,
windows, reference and VMAF model as above, but the live encoder's settings (`-tune zerolatency -g 48`, 1.6 s GOP).

| encode | W1 kbps / VMAF | W2 kbps / VMAF |
|---|---|---|
| today's live 720p rung (medium, zerolatency, ABR 1000k) | 1051 / 84.8 | 1055 / 86.9 |
| 1080p medium zerolatency CRF 25 / 27 / 29 | 2560 / 93.2, 2552 / 93.6, 2545 / 93.6 | 2510 / 94.9, 2468 / 94.9, 2381 / 94.7 |
| 1080p veryfast zerolatency CRF 29 / 33 | 2544 / 92.0, 1716 / 87.6 | 2358 / 93.2, 1431 / 88.3 |
| 1080p veryfast + lookahead CRF 27 | 1948 / 93.2 | 1559 / 93.3 |
| **1080p veryfast + lookahead CRF 29 (chosen)** | **1512 / 91.1** | **1210 / 91.4** |
| 1080p veryfast + lookahead CRF 31 | 1170 / 88.2 | 939 / 88.7 |

Under zerolatency (no B-frames, lookahead or mbtree) every CRF sits on the 2.5 Mbps ceiling, so the ceiling sets
the bits and the CRF hardly matters. Turning those three back on for the 1080p rung only gives +4.5 to +6.3 VMAF
over today's live 720p for 15 to 44% more bits, and 41 to 49% fewer bits than the zerolatency rung for 2.5 to 3.4
fewer points. CRF 27 costs about 29% more bits for +2 points; CRF 31 cuts the margin over 720p to 2 to 3 points.
The 2000k ceiling never bit on this class (same numbers as 2500k). The live-encoder-bandwidth ADR's CRF 24–25
covers 720p and below with B-frames; at 1080p the same perceived quality comes at a higher CRF, which matches the
VOD sweep's CRF 29.

## NVENC evidence

`reference/encode-sweep-2026-10-13/nvenc_1080_run.sh` (2026-10-20, `ROUND=1` and `ROUND=2`) ran the same two
windows on the GPU box inside `video-processor:latest` (ffmpeg 4.4.2, h264_nvenc, 472's `-preset fast`), one
encode at a time while encoder utilization was under 70%, scored on the Mac with the same VMAF setup
(`1080/nvenc/results_nvenc.csv`). The container needs the `video` GPU capability (`manager.js:347`); plain
`--gpus all` fails with `Cannot load libnvidia-encode.so.1`.

| NVENC encode (cap 2500k unless noted) | W1 kbps / VMAF | W2 kbps / VMAF |
|---|---|---|
| fixed target 2500k | 2656 / 95.9 | 2704 / 96.2 |
| cq 27 / 29 / 31 | 2494 / 95.5, 2491 / 95.6, 2483 / 95.7 | 2377 / 96.0, 2353 / 96.0, 2291 / 96.1 |
| constqp 29, no cap (scale check) | 2769 / 96.3 | 2104 / 96.0 |
| **cq 35 (chosen)** | **2092 / 94.9** | **1679 / 94.9** |
| cq 39 | 1297 / 91.7 | 1032 / 91.9 |
| p6 + hq + B-frames + lookahead + AQ, cq 29 / 33 / 37 | 2487 / 96.0, 2285 / 95.6, 1501 / 92.8 | 2347 / 96.5, 1937 / 95.8, 1258 / 93.3 |

What the numbers mean:
- NVENC cq and x264 crf are different scales. cq 29 asks for ~2.1-2.8 Mbps of quality on this class, so
  cq 27-31 all sit on the ceiling and the ceiling, not the cq, sets the bits. The rung therefore carries one
  value per encoder (`quality: { nvencCq: 35, x264Crf: 29 }` in `container/hls-ladder.js`).
- cq 35 matches the x264 pick's quality (VMAF 94.9 vs 94.7) at ~40% more bits (NVENC is less efficient than
  x264 slow). Against today's 720p rung on a 1080p screen it is +2.9 to +3.7 VMAF for +39 to +73% bits.
- The quality-tuned preset buys nothing in bits at VMAF ~94.7 (interpolated: W1 ~2.04 vs ~2.03 Mbps, W2 ~1.64 vs
  ~1.63) and takes ~2.5x the encode time on an engine that is already busy; only its worst frames are better
  (p1 +1.4). Not adopted.
- cq 39 lands at today's 720p quality, so it would not earn the rung.
