Lesson 01 · APX client 472

A cookie is not proof of authentication

A compact mental model for understanding why client 472 had a cookie in the browser, a session in MongoDB, and a running cron—yet every APX course request still returned 401.

The whole lesson: a session cookie is usually an opaque lookup key. Authentication exists only while the upstream server still maps that key to an authenticated session.

1. Separate the three concepts

A

Authentication

“Who are you?” Credentials or OTP establish identity and create a session.

B

Session

“Do I still remember you?” APX stores authenticated state under a random session ID.

C

Authorization

“May you do this?” A valid identity may still lack permission for a particular operation.

HTTP itself is stateless. Cookies let a server give a browser a small value in a Set-Cookie response header; the browser returns applicable values later in a Cookie request header. That exchange is defined by RFC 6265.

LOGIN APX → Browser: Set-Cookie: ci_session=S1; Path=/; Secure; HttpOnly LATER REQUEST Browser → APX: Cookie: ci_session=S1 APX session store: S1 → { user: 472, authenticated: true } APX → Browser: 200 courses JSON

The cookie does not normally contain the user, password, or permissions. It is closer to a cloakroom ticket: possession lets the server locate the real state. If APX deletes or invalidates the record behind S1, the browser can keep sending S1 forever and still be logged out.

2. This system has three copies of “session state”

Important: equality between the browser cookie and MongoDB does not prove validity. Only a request to an APX endpoint that requires authentication can prove that APX still accepts the session.

3. The proxy changes who owns cookie handling

The browser does not call APX directly for courses. It calls a Next.js route in admin-dashboard. That route reads the dashboard’s cookie, constructs an upstream Cookie header, calls APX, reads the result, and returns a new response to the browser.

Browser Cookie: ci_session=S1 │ ▼ admin-dashboard /api/proxy/courses manually sends Cookie: ci_session=S1 │ ▼ APX /paid_course4/get_all_courses validates S1 against APX's session store

This matters because the proxy is now a cookie boundary. If APX returns Set-Cookie: ci_session=S2, the proxy must deliberately decide how to carry that rotation back into the dashboard’s session system. A server-side HTTP client is not the user’s browser and does not automatically keep the browser’s cookie jar synchronized.

4. Replay the 472 incident

Client 472 had authenticated session S1

The browser and MongoDB held a usable APX session ID for org 8680775.

APX invalidated or expired S1

The exact initiating event is not retained. Likely candidates are logout/new login elsewhere, expiry, or missed keepalives during APX timeout/TLS failures.

The cron tested S1 against /dashboard

APX answered 307 Location: /login and issued a new anonymous ci_session=A1 for the login page.

The cron mistook rotation for renewal

It extracted A1 from every Set-Cookie without first proving the response was authenticated, then overwrote MongoDB’s S1 with A1.

The browser synchronized to A1

The dashboard’s 401 recovery copied the latest MongoDB value, but that value now represented an anonymous login-page session.

Courses and users kept failing

APX returned login HTML. The proxy recognized HTML where JSON was expected and deliberately translated that into HTTP 401.

Why the UI was misleading: isActive: true meant “the keepalive cron will process this record.” It did not mean “APX considers this session authenticated.” The live evidence was lastHttpStatus: 307, not the boolean.

5. Keepalive is not re-authentication

A keepalive can create activity so an idle timeout does not fire. It cannot overcome logout, revocation, an absolute timeout, a password/security event, or an already-expired session. Those require credentials or OTP again. OWASP distinguishes idle, absolute, and renewal timeouts and recommends lifecycle logging for creation, renewal, expiration, and destruction.

6. The production diagnostic loop

  1. Name the hop. Browser→proxy, proxy→APX, cron→APX, or browser→our backend?
  2. Use an auth-required probe. A public/read-session endpoint returning 200 proves almost nothing.
  3. Inspect status + intent together. 200 authenticated content differs from 307 /login, even if both responses contain Set-Cookie.
  4. Compare secrets by hash only. Record a short SHA-256 prefix and length; never print raw session IDs.
  5. Track transitions. Log “authenticated renewal,” “login redirect,” “network error,” and “revoked/expired” as different events.

7. Retrieval check

Mongo and the browser contain the same ci_session, but APX redirects an authenticated endpoint to /login. What is the strongest conclusion?

The cron receives 307 /login plus a new ci_session. What should it do?

8. What the permanent fix should encode

  • Update MongoDB’s session ID only after a proven authenticated response—at minimum, expected 200 content and no login redirect.
  • On 3xx → /login, preserve the previous ID for evidence, record an explicit expired/revoked state, and ask for re-authentication.
  • Rename or explain isActive as “keepalive enabled”; add a separate liveness/authentication status.
  • Teach the proxy how to handle legitimate session rotation instead of silently dropping upstream Set-Cookie.
  • Log timestamps, status, redirect target, and hashed old/new IDs—never raw cookies.
