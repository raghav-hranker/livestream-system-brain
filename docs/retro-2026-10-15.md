# Retro 2026-10-15: processes to automate

This covers 275 sessions from 2026-09-20 to 2026-10-14, across system-brain, webcam-livestream, the forks, nodejs-server and r2-backup.
Nothing has been applied; the user picks. Tool-call counts come from transcript digests, and some are lower bounds.

The common thread: the recipes already exist, in memory files and in `reference/scripts/`, but agents rebuild them anyway.
Saved scripts were reused in 2 of 15 health sessions. The memory recipes go unread when the session runs from another cwd.
A committed, named command fixes discovery, cost and permission denials together: an allow rule can match a stable script path, but not a fresh scratchpad file.

## 1. `qt-health` plus a morning health check (15 sessions, ~640 tool calls, ~24 auto-mode denials)
**Done 2026-10-15:** `reference/scripts/qt-health.sh` + LaunchAgent `com.hranker.qt-health` (08:30 daily).
Questions like "check the load on mongodb", "disk space on mongodb", "which query needs indexing", "why is it stuck at sending" and "probe why it happened again".
Every session re-runs the same steps:
- read 3–4 memory files
- pull `MONGO_URI` from `.env.development`
- `nc` the rs0 IPs
- write a scratchpad `top.js` with `$top`, `currentOp`, `rs.status`
- `ssh -i ~/.ssh/hranker-webserver2-2`, export the node v22 PATH, then `pm2 jlist` and the apache logs

In 81357963 the agent could not find `reference/scripts/mongo-top.js` and the user had to say "I had a script".

**Build:**
- `reference/scripts/qt-health [--mongo] [--box app|selectionway]`, wrapping `mongo-top.js`, `mongo-live.js`, `api_failure_probe.sh` and `notification_duplicate_probe.js`. It prints:
  - pm2 restarts and OOM
  - rs member health and lag
  - the top-10 slow ops
  - disk usage
  - 5xx rate and requests per second
  - notifications stuck in "sending"
- An allow rule for that path.
- A weekday morning scheduled run.

## 2. Livestream origin disk cleanup (fix, not a check), plus `ls-status` and `ls-heal`
The disk filled 3 times in 3 weeks:
- 2e466fce: at 50 GB the disk filled, ffmpeg died, and a live 472 class went off-air.
- f21120bd: 91 GB.
- 49f3de24: 93 GB.

`~/disk-cleanup.py` and `disk-report.js` already exist on the VM and verify bucket copies before deleting. Nothing runs them on a schedule. 49f3de24 ended with "a manual job again in roughly three weeks".

**Fix:** a cron at ~22:00 IST (the VM is off 23:00–07:00), keeping the bucket check intact.

Stuck or failed class repair cost 33–48 calls per session, in 66b770a6, 5ef14e6a, 7ca543db, 8a3fcdf4 and fdad825e. Each session wrote new one-off mongo, redis and ssh scripts.

**Build:**
- `ls-status <client|all>`, a single table covering:
  - rooms stuck in processing
  - failed or orphaned `transcoder.videos` per client, with retries marked
  - ended classes with an empty `class_link` or missing MP4s
  - Redis `job:*` stuck in PROCESSING
  - ffmpeg count per VM
  - disk use from Cloud Monitoring, which works while the VM is off
- A 07:15 IST run of `ls-status`.
- `ls-heal <classId...>` for the replay and MP4 re-queue loop that the user triggers by pasting id lists.
