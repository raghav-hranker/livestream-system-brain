Cookie-auth debugging card

APX / proxy systems · Treat raw session IDs as passwords.

Cookie present ≠ session valid ≠ user authorized. Only the server that owns the session store can confirm authentication.

The three truths

LayerQuestion
BrowserDid it store/send the cookie?
Proxy / MongoDid we forward/save the same ID?
Upstream APXDoes this ID still map to an authenticated user?

Headers to inspect

  • Request: Cookie
  • Response: Set-Cookie
  • Redirect: status + Location
  • Content: expected JSON vs login HTML

Secret-safe comparison

Log length plus a short SHA-256 prefix, e.g. len=32 hash=c2c990a9503b. Never log the raw cookie.

Five-step triage

  1. Name the exact request hop.
  2. Probe an auth-required endpoint.
  3. Check status, redirect, content, and cookie rotation together.
  4. Compare browser/DB IDs by hash.
  5. Ask APX—not a local boolean—whether the session is valid.

Interpretation

200 expected contentAuthenticated
307 → /loginExpired/revoked
HTML where JSON expectedOften login page
Network timeoutUnknown; do not mutate ID
New cookie on authenticated 200Legitimate rotation candidate

Safe state rule

Persist a rotated session ID only after proving the response is authenticated. On login redirect or ambiguous failure, preserve the previous ID and require re-authentication.
